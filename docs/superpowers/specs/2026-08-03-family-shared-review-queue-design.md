# 家庭共享与今日待复习清单设计

> 日期：2026-08-03  
> 范围：字卡库人工加入今日待复习、家庭成员共享数据、现有数据安全迁移。  
> 状态：待用户书面复核后进入实施计划阶段。

## 1. 目标

本次调整解决两个问题：

1. 字卡库中的“选择复习”不再直接开始复习，而是将选中字卡加入首页“今日待复习”。
2. 数据从“单个微信拥有”升级为“家庭拥有”，同一家庭的多个微信账号共享孩子、字卡、分类和复习进度，不同家庭之间严格隔离。

本次不改变熟练度等级、自动复习周期、字卡排序和现有首页“管理本次”批次复习能力。

## 2. 已确认产品决策

- 采用“家庭、家庭成员、孩子”三级模型，即方案 B。
- 当前线上已有 1 个孩子和 69 张字卡，这些数据必须全部保留。
- 当前已有数据对应的微信 `openid` 自动成为家庭创建人和 `owner`。
- 现有孩子、字卡、分类和复习记录采用原地补充 `familyId` 的方式迁移，不删除记录、不重建字卡 ID、不重置熟练度、复习次数或最后复习时间。
- 其他微信通过家庭随机码加入。
- 加入者已有数据时允许合并；重复数据以目标家庭原数据为主，不静默覆盖。
- 人工加入但当天未完成的字卡跨天继续保留，直到完成、取消或字卡被删除。
- 每个家庭成员独立设置微信提醒时间、提醒开关和订阅额度。

## 3. 方案选择

采用独立家庭实体和成员关系：

```text
可信微信 OPENID
  -> active family_members 记录
  -> families 家庭
  -> children 孩子
  -> cards / categories / review_sessions / review_assignments
```

不采用仅在 `users` 上增加 `familyId` 的简化方案，因为它无法清晰表达成员角色、邀请码、加入历史和后续退出关系；也不采用多个微信各存一份再同步的方案，因为复制同步容易造成熟练度冲突和跨家庭数据泄漏。

## 4. 字卡库加入今日待复习

### 4.1 页面交互

1. 字卡库保留“选择复习”入口和现有多选交互。
2. 进入选择模式后，底部按钮由“开始复习”改为“加入今日待复习”。
3. 未选择字卡时按钮不可用；每次仍最多选择 50 张。
4. 提交成功后退出选择模式，提示“已加入 N 张，M 张已在列表中”，并切换到首页。
5. 提交失败时保留当前选择状态，提示重试，不进入复习页。

### 4.2 云端人工清单

新增 `review_assignments` 集合：

```js
{
  _id: 'auto',
  familyId: 'family_xxx',
  childId: 'child_xxx',
  cardId: 'card_xxx',
  scheduledDate: '2026-08-03',
  source: 'manual',
  status: 'pending',
  addedByOpenid: 'openid_xxx',
  createdAt: 'serverDate',
  completedAt: null,
  cancelledAt: null
}
```

同一家庭、同一孩子、同一字卡只能存在一条有效的 `pending` 人工任务。批量加入必须幂等：已经在人工清单或系统自动待复习中的字卡不得在首页重复出现。

### 4.3 首页清单生成

首页“今日待复习”由以下两部分合并：

```text
系统按熟练度和复习周期计算出的到期字卡
  + scheduledDate <= 今天且 status = pending 的人工任务
  -> 按 cardId 去重
  -> 使用现有复习优先级排序
```

人工任务引用的字卡若已删除、停用、转移失败或不属于当前家庭，则不返回并将任务取消。人工任务完成前跨天保留，避免用户选择的复习内容在午夜丢失。

### 4.4 与现有复习流程的关系

- 首页普通“开始复习”：复习合并后的完整今日清单。
- 首页“管理本次”：继续从完整今日清单中选择本批字卡，并使用现有 `replace` 临时批次模式。
- 字卡库：只负责向云端人工清单添加字卡，不再写入本机 `append` 临时队列，也不直接打开复习页。
- 复习完成：在更新字卡复习状态的同一事务中，将本轮卡片对应的 `pending` 人工任务标记为 `completed`。

## 5. 家庭数据模型

### 5.1 新集合

#### `families`

```js
{
  _id: 'family_xxx',
  name: '我的家庭',
  createdByOpenid: 'openid_xxx',
  status: 'active',
  createdAt: 'serverDate',
  updatedAt: 'serverDate'
}
```

#### `family_members`

```js
{
  _id: 'auto',
  familyId: 'family_xxx',
  openid: 'openid_xxx',
  role: 'owner',
  status: 'active',
  reminderEnabled: true,
  reminderTime: '20:00',
  joinedAt: 'serverDate',
  updatedAt: 'serverDate'
}
```

第一版角色只有：

- `owner`：生成邀请码、查看成员、管理家庭关系。
- `member`：共同查看、录入、编辑、删除和复习家庭字卡。

#### `family_invites`

```js
{
  _id: 'auto',
  familyId: 'family_xxx',
  codeDigest: 'server generated digest',
  status: 'active',
  expiresAt: 'serverDate',
  maxUses: 1,
  usedCount: 0,
  createdByOpenid: 'openid_xxx',
  createdAt: 'serverDate',
  usedAt: null,
  usedByOpenid: null
}
```

邀请码使用排除 `0/O`、`1/I` 等易混字符的 8 位随机码，单次有效，24 小时过期。重新生成时立即作废此前未使用的邀请码。数据库只保存服务端摘要；加入接口限制连续失败次数，并统一返回“家庭码无效或已过期”。

#### `family_merge_jobs`

记录加入者现有私人家庭向目标家庭合并的预览、执行状态、数量、字卡和分类映射、失败原因及重试信息。合并操作使用唯一请求 ID 保证幂等。

### 5.2 现有集合调整

| 集合 | 调整 |
|---|---|
| `users` | 增加 `activeFamilyId`；订阅额度继续按微信用户保存 |
| `children` | 增加 `familyId`；`ownerOpenid`只作为迁移兼容字段，不再作为最终授权依据 |
| `cards` | 增加 `familyId`和`createdByOpenid`；保留现有`childId`和原始`_id` |
| `categories` | 增加 `familyId`和`createdByOpenid`；分类仍按孩子隔离 |
| `review_sessions` | 增加 `familyId`和`reviewedByOpenid` |
| `reminder_logs` | 增加 `familyId`和接收提醒的成员`openid` |
| `subscription_events` | 保持用户级归属，不转为家庭共享 |

孩子昵称和认字日属于家庭共享设置；提醒开关、提醒时间和订阅额度属于各微信成员个人设置。

## 6. 服务端授权与家庭隔离

所有业务云函数必须从 `cloud.getWXContext().OPENID` 获取可信身份，不能接受前端传入的 `familyId` 作为授权依据。

统一授权顺序：

1. 用 `openid` 查询状态为 `active` 的 `family_members`。
2. 确认该成员的家庭与 `users.activeFamilyId` 一致。
3. 查询目标孩子并确认 `child.familyId` 等于当前家庭。
4. 所有后续查询同时带上 `familyId + childId + status` 条件。
5. 按文档 ID 读取字卡、分类或复习任务后，仍需重新校验其 `familyId` 和 `childId`。

字卡查重范围固定为：

```text
familyId + childId + normalizedContent + active status
```

因此不同家庭可以分别拥有内容相同的字卡，但记录、分类、熟练度、复习次数、人工任务和历史互不关联。禁止按 `normalizedContent` 做跨家庭全局去重。

需要改造授权的云函数包括：

- `syncSettings`
- `cardService`
- `categoryService`
- `reviewService`
- `sendReminder`

`subscriptionService`继续按当前微信用户处理订阅额度，但返回和扣减时必须绑定实际接收提醒的成员。

## 7. 现有 1 个孩子和 69 张字卡迁移

### 7.1 迁移硬约束

- 不删除任何现有活动数据。
- 不新建替代字卡，不改变现有字卡 `_id`。
- 不重置孩子设置、字卡分类、自定义组词、熟练度、复习次数、最后复习时间和复习历史。
- 当前已有数据的 `ownerOpenid` 成为新家庭的 `createdByOpenid`，并成为唯一初始 `owner`。
- 迁移前后必须分别核对活动孩子数为 1、活动字卡数为 69；数量不一致时停止开放家庭入口。

### 7.2 发布迁移顺序

采用兼容式分阶段迁移，避免一次性替换授权导致现有用户无法访问：

1. 发布支持旧 `ownerOpenid` 和新 `familyId` 双读的兼容代码，但尚不开放家庭入口。
2. 为当前微信创建一个 `families` 记录。
3. 创建该微信对应的 `family_members`，角色为 `owner`。
4. 将 `users.activeFamilyId` 指向新家庭。
5. 原地为现有孩子补充 `familyId`。
6. 原地为该孩子关联的 69 张字卡、分类、复习记录和提醒日志分批补充同一个 `familyId`。
7. 校验迁移前后数量、字卡 ID 集合、关键复习字段和孤儿引用。
8. 创建迁移快照和审计结果；校验通过后才启用严格家庭授权。
9. 严格家庭授权稳定后，才在设置页开放生成家庭码和加入家庭。

旧 `ownerOpenid` 字段在首版保留作为审计和紧急回滚依据，不立即物理删除。

## 8. 新成员加入与已有数据合并

### 8.1 加入限制

- 一个微信账号同一时间只能有一个活动家庭。
- 账号首次使用时自动建立只有自己的私人家庭，因此已有数据始终有明确归属。
- 只有当前私人家庭仅包含自己一个活动成员时，才能直接合并加入另一个家庭。
- 如果当前家庭已有其他成员，则禁止直接迁移，避免携带第三人的共享数据。

### 8.2 加入流程

1. 加入者输入家庭码。
2. 服务端校验邀请码状态、有效期、使用次数和创建者权限。
3. 服务端生成合并预览：孩子数量、字卡总数、重复字卡数、独有字卡数和分类冲突数。
4. 前端展示预览，加入者二次确认。
5. 创建 `family_merge_jobs`并锁定源私人家庭的写操作。
6. 完成分类映射、字卡迁移、复习历史映射及人工任务迁移。
7. 所有校验通过后，创建目标家庭的 `member`关系并切换`users.activeFamilyId`。
8. 将源私人家庭标记为`merged`，解除迁移锁，消费邀请码。

加入失败时，用户继续留在原私人家庭；不得提前切换 `activeFamilyId` 或提前消费邀请码。

### 8.3 重复数据规则

重复字卡按“目标家庭 + 目标孩子 + 标准化内容”判断：

- 目标家庭的字卡 `_id`、内容、熟练度、复习次数、最后复习时间和状态保持不变。
- 来源家庭同名字卡不再创建第二张活动字卡。
- 自定义组词和分类进行非破坏性并集，不删除目标家庭已有内容。
- 来源家庭复习历史中的字卡引用映射到目标字卡 ID，历史快照和完成时间保留。
- 来源家庭独有字卡迁移到目标家庭并保留原字卡 ID 与复习字段。
- 孩子名称、认字日等冲突以目标家庭设置为准，预览页面明确说明不会覆盖。

## 9. 设置页调整

在现有提醒设置之外新增“家庭共享”卡片：

- 展示当前家庭和成员数量。
- `owner`可生成、复制或重新生成家庭码。
- 新账号或仅有自己一个成员的私人家庭可输入家庭码。
- 加入前展示数据合并预览和目标家庭名称。
- 合并过程中显示明确状态并禁止重复提交。
- 非`owner`不显示生成邀请码操作。

现有提醒设置迁移为当前微信成员的个人设置；孩子昵称和认字日仍作为家庭共享设置保存。

## 10. 异常与一致性处理

- 批量加入今日清单部分重复：返回新增数和已存在数，不整体失败。
- 某张字卡加入期间被删除：跳过该卡并返回失效数。
- 两个成员同时加入同一张字卡：通过服务端幂等键只保留一个 `pending`任务。
- 邀请码被同时使用：只允许第一个有效请求消费成功。
- 合并过程中任一步失败：保留合并任务和映射，按请求 ID 从安全断点重试。
- 合并锁定期间：来源家庭的新增、编辑、删除和复习提交返回“家庭数据正在合并，请稍后重试”。
- 家庭成员权限被撤销后：本地缓存立即失效，下一次云请求不得继续读取原家庭数据。

## 11. 缓存隔离

现有缓存键不包含家庭信息。家庭切换成功后必须清除以下业务缓存：

- 用户和孩子缓存
- 字卡与分类缓存
- 今日计划缓存
- 临时复习队列
- 字卡库筛选意图

重新启动会话后按新的 `activeFamilyId` 拉取数据。后续缓存值应记录 `familyId`，读取时发现家庭不一致立即作废，防止同一手机切换账号或家庭后显示旧数据。

## 12. 测试与验收

### 12.1 自动测试

- 字卡库选择后调用人工清单接口，不再进入复习页。
- 首页正确合并自动到期和人工字卡并按 `cardId` 去重。
- 人工字卡跨天保留，完成、取消或删除后消失。
- 同一家庭两个微信看到一致的孩子、字卡、分类和复习结果。
- 非家庭成员无法使用猜测的 `childId`、`cardId` 或 `categoryId`访问数据。
- 不同家庭的同名字卡可以独立存在并保持不同复习状态。
- 邀请码过期、重复使用、错误尝试和并发消费行为正确。
- 合并预览数量正确，重复字卡目标数据优先，独有字卡完整迁移。
- 合并失败不会切换活动家庭，重试不会重复创建字卡或成员。
- 家庭切换后旧缓存不会被展示。
- 每个成员的提醒时间、开关和订阅额度互不覆盖。

### 12.2 存量数据验收

迁移前后逐项比对：

- 活动孩子：1 -> 1。
- 活动字卡：69 -> 69。
- 69 张字卡 `_id` 集合完全一致。
- 每张字卡内容、分类、自定义组词、熟练度、复习次数和最后复习时间完全一致。
- 当前微信是新家庭唯一初始`owner`。
- 当前微信迁移后可正常查看、录入、编辑、删除和复习原有字卡。
- 未加入家庭的其他微信无法读取这 69 张字卡。

### 12.3 微信开发者工具验收

1. 迁移现有账号，确认首页和字卡库仍显示原有数据。
2. 从字卡库选择非到期字卡加入今日待复习，确认不直接进入复习页。
3. 返回首页确认新增字卡出现且无重复。
4. 创建家庭码，用另一个微信加入并确认合并预览。
5. 两个微信分别新增、编辑和完成复习，确认数据实时一致。
6. 使用第三个未加入家庭的微信尝试访问同一资源，确认被拒绝。
7. 在另一个独立家庭创建同名字卡，确认两边进度互不影响。

## 13. 实施阶段建议

1. 云端人工待复习任务和字卡库交互。
2. 家庭、成员及统一授权基础设施。
3. 现有 1 个孩子、69 张字卡的兼容迁移和核验工具。
4. 家庭邀请码与加入流程。
5. 已有数据合并任务、冲突预览和失败恢复。
6. 成员级提醒迁移、全链路回归与灰度开放。

## 14. 非目标

- 第一版不支持一个微信同时切换多个活动家庭。
- 第一版不支持一个已有多成员家庭整体加入另一个家庭。
- 第一版不提供复杂成员权限矩阵，`member`默认可共同维护家庭字卡。
- 不改变现有复习间隔和熟练度算法。
- 不进行与家庭共享无关的页面重构或代码优化。
